## 3. Chi tiết kỹ thuật

### 3.1 Per-day, không per-category

Unified model mở khoá lựa chọn này:

| | per-category | **per-day** ✅ |
| :-- | :-- | :-- |
| Prompt file | 10 | **1** |
| Chống trùng bữa / cruise | Cần matrix code | Agent thấy cả ngày ⇒ **tự tránh** |
| Context mỗi call | Toàn trip | Chỉ 1 ngày ⇒ ngắn, rẻ, chính xác |
| Isolation lỗi | Mất 1 category toàn trip | Mất 1 ngày ⇒ retry riêng |

Trip-level (visa, flight, through-guide, SIM) = **1 call riêng** `day = null`, cùng agent, khác context block.

```python
drafts = await asyncio.gather(*[
    drafter.run(day_prompt(d), deps=DrafterDeps(profile, base_params, d, repos))
    for d in day_contexts + [trip_level_ctx]
], return_exceptions=True)          # 1 ngày lỗi ⇒ ngày đó rỗng, 7 ngày kia vẫn có
```

### 3.2 Không hard rule chống trùng — đưa dữ kiện vào context

```yaml
day: 3
destination: "Ha Long Bay"
overnight_type: cruise                               # hotel | cruise | train | none
meals_already_covered: [breakfast, lunch, dinner]
transport_already_covered: true
previous_day_stay_includes: [breakfast]
```

Agent không đề xuất bữa nào vì **không còn bữa nào để đề xuất**. Dữ kiện lấy từ `staysReconciler` đã có.

> Rule là thứ ta viết khi lười đưa dữ kiện.

### 3.3 Hai tool

| Tool | Trả về | Luật |
| :-- | :-- | :-- |
| `get_destination_brief` | POI đã lọc theo `mobility_level` + `interests`, kèm cường độ vận động, số bậc thang, thời lượng; mùa vụ; visa policy | ≤ 8 dòng |
| `find_similar_past_days` | Dịch vụ đã bán ở điểm này cho archetype + style này, kèm tần suất | ≤ 8 dòng |

**Ba luật cho mọi tool**: filter ở SQL không ở LLM · trả ≤ 8 dòng · **không trả giá tuyệt đối**.

`find_similar_past_days` thay prompt engineering bằng dữ liệu thật:

```
Hội An · gia đình có trẻ · luxury — 12 quotation đã bán:
  Vé phố cổ            12/12  100%
  Lớp làm đèn lồng      9/12   75%
  Đạp xe Trà Quế        7/12   58%
```

Sprint này tool còn nghèo (ít lịch sử). Nó **tự tốt lên** mà không ai sửa prompt.

### 3.4 Prompt tự đồng bộ với config

```yaml
units: |
  Chọn `unit` từ danh sách sau, cấp đúng biến nó cần:
  {{ unit_catalog }}          # render từ formulas.yaml

context: |
  === SỐ LƯỢNG MẶC ĐỊNH (đã tính sẵn — chỉ override khi có lý do) ===
  {{ base_params }}           # render từ param_rules.yaml
```

Thêm `unit` vào YAML ⇒ prompt tự biết. **Không tồn tại trạng thái "quên cập nhật prompt"** — vì không có chỗ nào để quên.

### 3.5 Luật trong prompt

```
- KHÔNG BAO GIỜ nhắc tới số tiền.
- Mỗi dịch vụ chọn ĐÚNG 1 phương án. Không đề xuất phương án thay thế.
- Chỉ đặt tariff_id khi tool trả về đúng dịch vụ đó, ngược lại null.
  (tariff_id = định danh rate header trong catalog — LLM chỉ **chuyển tiếp** id tool đưa, không tự chế.)
- params: chỉ đặt rooms/vehicles/guides/boats/sessions khi ngày này KHÁC mặc định.
  Khi override, note PHẢI nói rõ vì sao.
- KHÔNG đặt pax, nights, days, legs, segments, meals — hệ thống tự tính.
- DÙNG TOOL TRƯỚC KHI ĐOÁN.
- CHECKLIST 10 DANH MỤC: duyệt từng mục, bỏ qua nếu ngày này không cần.
```

### 3.6 Guard rails

```python
GUARDS = {"max_tool_calls": 6, "timeout_s": 25, "on_error": "skip_day"}
DRAFTER_MODE = os.getenv("DRAFTER_MODE", "on")   # "off" ⇒ skeleton rỗng, sale làm tay
```

### 3.7 Endpoint SSE

`POST /api/v2/quotations/{id}/service-lines:draft` → `text/event-stream`

```
event: skeleton   data: {"days":[{day:1,date:"…",destination:"…"}, …]}
event: day        data: {"day":1,"lines":[…]}
event: day        data: {"day":2,"lines":[…]}
event: error      data: {"day":5,"reason":"timeout"}
event: done       data: {"summary":{…},"revision":42}
```

Grid render khung ngày ngay từ `skeleton`, từng nhóm điền dần. Ngày `error` ⇒ nhóm rỗng + nút *Soạn lại ngày này*.

## 8. Forward-compat với Phase 2 (14.0) — không đổi scope sprint này

### 8.1 `find_services` — server resolve giá, LLM chỉ trả định danh

Đây là điểm dễ trượt nhất khi Phase 2 tới. Ba luật tool ở §3.3 (**filter ở SQL · ≤ 8 dòng · không trả giá tuyệt đối**)
**vẫn giữ nguyên** khi catalog có dữ liệu. `find_services` trả về:

```text
✅ product_id · tariff_id (rate header) · title · unit · supplier_name · độ phù hợp
❌ amount_minor · unit_price · bất kỳ con số tiền nào
```

Giá được lấy **sau khi** LLM trả `ServiceDraft`, bằng code thuần `core/rules/rate_selection.py`:
`(product_id, service_date, pax, occupancy_basis) → price_line → unit_price_minor`.

Lý do: LLM chọn giá = LLM có thể bịa giá, và không có chỗ nào ghi lại **vì sao** rate đó được chọn.
`rate_selection` là pure, deterministic, và trả `RATE_CONFLICT` khi hai rate hoà — thứ LLM không làm được.

Hệ quả cho code sprint này:

| Nơi | Ràng buộc |
| :-- | :-- |
| `services/drafter_tools.py` | Hai tool hiện tại đã tuân thủ. Thêm tool thứ ba ở Phase 2 phải qua **cùng** helper `_strip_money()` — viết helper đó ngay bây giờ, dùng cho 2 tool đang có |
| `services/service_drafter.py` | Sau khi gom `DayDraftResult`, có một bước *"resolve price"* — sprint này là **no-op** (catalog rỗng ⇒ `price_source='missing'`). Đặt sẵn hook, đừng nhét vào Phase 2 |
| `schemas/service_draft.py` | `#D0` **không đổi**. Không thêm `product_id`, không thêm `price_line_id` vào hợp đồng LLM — đó là kết quả của server |
